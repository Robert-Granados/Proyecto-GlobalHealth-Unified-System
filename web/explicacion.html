Guía rápida del proyecto

GlobalHealth Unified System

Una arquitectura híbrida de bases de datos para una corporación de clínicas. Cada tecnología guarda un tipo de dato distinto y cada una hace el trabajo para el que es mejor.

🇨🇷 Costa Rica 🇬🇹 Guatemala 🇵🇦 Panamá Todo en Docker

1 ¿Qué es?

Es el sistema de datos de una red de clínicas: guarda pacientes, empleados, signos vitales, expedientes clínicos y telemetría de dispositivos. No usa una sola base de datos: usa tres motores especializados detrás de una sola API.

PostgreSQL 16 Datos clínicos estructurados

Clínicas, pacientes, médicos y enfermeros con un modelo objeto-relacional (tipos compuestos, herencia de tablas, identidad UUID). Corre en dos nodos: un master que escribe y una réplica que solo lee.

SQL Server 2022 Expedientes en XML

Los expedientes clínicos viajan como XML validado contra un XSD registrado dentro del motor. Si el XML es inválido, la propia base de datos lo rechaza con el error exacto.

MongoDB Atlas Telemetría

1.000 pacientes, 5.000 sesiones y 50.000 logs BSON en el modelo Paciente → Sesión → Log. El panel lista, filtra, agrega y ejecuta CRUD sobre el cluster real mediante la API.

Node.js API La puerta de entrada

Un backend pequeño con dos conexiones físicas separadas: una exclusiva para escribir en el master y otra exclusiva para leer de la réplica. Sin fallback entre ellas.

3 ¿Cómo funciona? Cinco flujos

El recorrido completo de un dato, paso a paso.

  1. El usuario llena el formulario “Registrar signos vitales” en el panel.
  2. El navegador envía POST /api/signos-vitales a nginx, que lo reenvía a la API.
  3. La ruta llama exclusivamente a queryWrite → writePool.
  4. El INSERT se ejecuta en el master de PostgreSQL.
  5. El master escribe el cambio en su WAL (bitácora física).
  6. La réplica recibe el WAL por streaming y lo aplica: el dato ya se puede leer.
  1. El panel pide GET /api/dashboard/signos-vitales.
  2. La ruta llama exclusivamente a queryRead → readPool.
  3. El SELECT se ejecuta en la réplica hot-standby, nunca en el master.
  4. El master queda libre de consultas: solo atiende escrituras.
Sin fallback: si la réplica cae, la lectura falla de forma visible. El sistema no se reconecta al master “para salvar la consulta”: esa separación física es un requisito del diseño, no un descuido.
  1. Desde el panel (sección “Expediente clínico XML”) se envía el documento a POST /api/expedientes.
  2. La API lo inserta tal cual en la columna Documento xml(dbo.ExpedienteClinicoXsd) — no valida nada por su cuenta.
  3. SQL Server valida contra el XSD registrado: patrones de cédula y CIE-10, enumeraciones de país/severidad, fechas, firma médica obligatoria, hasta 20 diagnósticos…
  4. Si algo no cumple, el motor rechaza el insert y la API devuelve 422 con el número y mensaje exactos del motor (ej. 6908 · Expected element: FirmaMedico), que el panel muestra en rojo.
La aplicación no contiene ninguna librería de validación XSD: la fuente de autoridad es la propia base de datos. Los botones de preset (“Sin firma médica”, “Fecha inválida”) permiten ver los rechazos en vivo.
  1. El formulario “Registrar médico” del panel envía POST /api/medicos con los datos básicos.
  2. La API construye el INSERT a gh_obj.medico_t —tabla hija de empleado_base por INHERITS— armando los tipos compuestos: ROW(...)::direccion_t, contacto_t con su array de teléfonos y el array de especialidad_t.
  3. El master valida dominios y CHECK (identificación, correo, colegiado, mayoría de edad…); si algo falla responde 400/409 con el nombre de la restricción.
  4. El WAL viaja a la réplica y la tabla del panel —que lee con GET /api/medicos desde la réplica— muestra al nuevo médico usando el método nombre_completo(medico_t).
El objeto_oid (UUID) es la identidad lógica del objeto y clinica_ref se asigna a la clínica del país elegido: es la referencia (REF) del modelo objeto-relacional.
  1. El panel consulta GET /health/mongo, el resumen agregado y la lista paginada de logs.
  2. Los filtros de paciente, tipo y calidad se traducen a consultas MongoDB con límites y ordenamiento.
  3. Nueva lectura envía POST /api/telemetria; la API comprueba que la sesión padre exista y asigna un logId único mediante un contador atómico.
  4. El lápiz ejecuta PUT /api/telemetria/:logId y la papelera ejecuta DELETE tras confirmación.
  5. Después de cada escritura se vuelven a consultar Atlas, los conteos y la agregación; la interfaz no simula datos localmente.
Los rangos se validan por tipo: frecuencia cardiaca 20–250 lpm, SpO2 0–100 % y temperatura 25–50 °C. La unidad se deriva en la API y una sesionId inexistente se rechaza.

4 Controles críticos del diseño

Las reglas que el sistema se obliga a cumplir al arrancar y en cada operación.

PG

Separación física verificada

Al arrancar, la API exige pg_is_in_recovery()=false en el pool de escritura y =true en el de lectura, y que ambos resuelvan direcciones físicas distintas. Si no, el proceso aborta.

MDB

Integridad documental en Atlas

Índices únicos para paciente, sesión y log; relación padre obligatoria, URI inyectada por entorno, consultas con $lookup y CRUD validado a través de una interfaz funcional.

!

Sin fallback ni promoción

No hay proxy, balanceador ni reintento cruzado. Que las lecturas sobrevivan a una caída no implica que las escrituras sobrevivan.

XML

Validación dentro del motor

El XSD vive en SQL Server como XML SCHEMA COLLECTION. Cualquier asignación a la columna tipada —incluido XML DML— se valida contra el esquema registrado.

OR

Modelo objeto-relacional real

Tablas tipadas (OF tipo), herencia con INHERITS para médicos y enfermeros, dominios, y UUID como identidad de objeto estable.

5 ¿Cómo se levanta?

Cuatro pasos desde la raíz del repositorio (Windows, PowerShell).

:: 1. Crear el archivo de secretos (cambiar las contraseñas)
Copy-Item .env.example .env

:: 2. Levantar todos los contenedores
docker compose up -d --build

:: 3. Inicializar la capa XML en SQL Server (una sola vez)
docker compose run --rm sqlserver-init

:: 4. Verificar la separación master/réplica del backend
.\infra\postgres\validar-backend.ps1
Panel funcional en http://localhost:8090 · esta explicación en http://localhost:8090/explicacion.html
